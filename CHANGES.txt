= 0.3.0 =
captureMessage(message, level): sends a message event of the app's own at debug, info, warning, error or fatal. It is not queued: a call before start rejects with the reason, on both platforms. An empty message and a level outside the five names are refused before they reach native, as the other calls refuse them
addBreadcrumb and clearBreadcrumbs: the page's breadcrumbs reach the native scope, so a native crash carries what the page did before it. The JavaScript levels log and critical are sent as debug and fatal, a breadcrumb the two platforms would read differently is refused, and before start they are kept in order, the last hundred, and start adds them
setExtras, close and isEnabled. An extra is text on both platforms (sentry-android's scope takes only a string): a string as it is, anything else as its JSON, null or undefined removes it. close stops the SDK, flushing it, and answers closed or not running; a start after it starts it again, what the page set meanwhile is kept for that start and allowCrash is not. isEnabled says whether the SDK is running, whoever started it
start takes enableNativeCrashHandling, enableWatchdogTerminationTracking (iOS), debug, sendDefaultPii, maxBreadcrumbs, sampleRate, attachStacktrace, attachThreads (Android), sessionTrackingIntervalMillis and enableNdkScopeSync (Android). An option that is not given is left to the SDK, and one of the wrong type is refused in JavaScript, the promise rejecting with the option's name
getDeviceInfo(): the OS name and version, the device model and the app's release and build, read from the system with no SDK running. A page cannot read them from the web view: Safari's user agent on an iOS 26.3 simulator says iPhone OS 18_7
www/scope-sync: bindScope(scope) wraps the setters of a scope of the JavaScript SDK (setUser, setTag, setTags, setExtra, setExtras, setContext, addBreadcrumb, clearBreadcrumbs) so that what the page sets also goes to the plugin. No dependency: the scope is taken by its shape, window.SentrySdk is looked up at every call, and a failure on the way goes to onError and never to the page
README: the SDKs' own log is not forwarded to the page, and why: sentry-android has a stable logger option, sentry-cocoa 9.30.2 only a hook its source marks as removable in any minor release
CI: a push to main runs only parity and unit before it publishes (the pull request already ran the platform suites), and ci.yaml started by hand on main with publish ticked publishes the version in package.json at once, for when a package is wanted now

= 0.2.0 =
Android: sentry-android 8.61.0 (it was 8.60.0). Its fixes are about callbacks that throw, which this plugin sets none of, and Session Replay, which it never turns on; the NDK module it carries moves from sentry-native 0.17.2 to 0.17.3
Android: the sentry-android artifact is the plugin variable SENTRY_ANDROID_ARTIFACT, and the default is sentry-android-core. The plugin took sentry-android before, which brings the NDK module (crashes in native C and C++ code) and Session Replay along. An app that wants native crashes installs with SENTRY_ANDROID_ARTIFACT=sentry-android; one that did not know it had them loses them without it
crash() is refused, on both platforms, unless the last accepted start was given allowCrash: true. A device probe has to pass the option
The wrapper settles what the platforms read differently: a number in a user's id, email or username is its text, an empty string and null leave the field out, and a user, tags or a context of another type are refused with the reason. An array as a context used to be a removal, and an id that was a number was kept on Android and dropped on iOS
CI: a weekly workflow compares the sentry-cocoa and sentry-android pins with their latest releases and opens a pull request that moves the pin when one is behind, a major release included, and starts CI on its branch (ci.yaml can be started by hand now, and such a run never publishes). Dependabot could not: its Swift jobs failed, and it does not read plugin.xml. Its two Swift entries are gone
iOS: sentry-cocoa 9.30.2 (it was 9.30.1). Its fixes are mostly in what runs inside a crashing or busy app: crash report buffer overflows, a deadlock in the crash handler, and two EXC_BAD_ACCESS crashes of the SDK itself, in the network tracker and in reading the cellular network technology
start refuses a dsn the SDK cannot parse, on iOS too: sentry-cocoa starts without a dsn and sends nothing, and the plugin used to answer started and then answer already started to every corrected attempt
a user, tags or a context set before start are kept, answered queued, and applied by start (the last change of each key), instead of being answered set and lost
whether the SDK is running is the SDK's to say, not a flag of the plugin instance: a plugin instance made again after an Activity is recreated, or an SDK the app started itself, answers already started and works on the running SDK
An end-to-end test: the demo app, built with the plugin installed the way an app installs it, crashes itself on an Android emulator and on an iOS simulator and sends its report to an ingest endpoint on the runner, and the test reads the SDK and its version, the release, the environment, the user, the tags, the context and the exception. No Sentry account and no secret, so it runs for every pull request
Every name derives from the plugin id, on both platforms: window.SentrySdk, the SentrySdk service, class and Swift target, and the Android package io.github.maximbelov.sentrysdk, with the Kotlin source under a slash-separated directory (they were SentryNative and io.github.maximbelov.sentry). Breaking: an app calls window.SentrySdk
test/android builds with the Gradle and Android Gradle plugin of the cordova-android it tests against, and Dependabot leaves them alone
Engines: cordova-ios 8.0.1 or newer and cordova-android 15.1.0 or newer (they said 8.0.0 and 12.0.0). On cordova-ios 8.0.0 the build fails when the plugin is already in the project as the platform is added, which is what cordova prepare does on a fresh clone: the plugins' Swift package stays at iOS 13 against the 15 the SDK needs. 15.1.0 is the oldest cordova-android the tests build with
Android: plugin.xml turns Kotlin on and no longer sets its version. An app that declares none now gets cordova-android's own default (2.1.21 in 15.1.0) instead of the 2.1.0 this plugin injected; an app's own GradlePluginKotlinVersion was never overridden. The demo app declares no Kotlin and no deployment-target setting any more, so the end-to-end test proves that the plugin's own are enough
Types: start answers 'started' | 'already started', setUser 'set' | 'cleared' | 'queued', setTags and setContext 'set' | 'queued', and crash is Promise<never>; they were all Promise<void> while native answered strings. A test compiles a sample consumer against them
iOS: the enableMetricKit option, which sentry-cocoa points at instead of app hang tracking. enableAppHangTracking and appHangTimeoutInterval are marked deprecated: sentry-cocoa removes app hang tracking in v10
README: the late start and what it costs, the web view's own crashes, who owns sessions, setting the user early, what is sent, symbols, versions of the SDKs, coming from sentry-cordova. The reasons for the platform minimums are measured ones, and the comments in plugin.xml say what was measured
CI: the committed build of www/ is checked in every pull request, and a change to src/www starts the native tests. tests/ follows the plugin's version, and a test holds it

= 0.1.2 =
Android: arrays inside a context are converted element by element, so no JSONObject, JSONArray or JSONObject.NULL reaches Sentry
Android: sentry-android 8.60.0 by default; plugin.xml declares the android XML namespace it uses
iOS: Xcode 26 is required, SwiftPM 6.1 (Xcode 16.4) cannot resolve sentry-cocoa 9.x pinned by version; the iOS tests run on macos-26
iOS: appHangTimeoutInterval is read as a number, so an integer value is applied too
plugin.xml enables Kotlin for Android and sets the iOS deployment target to 15.0, so an app that never set them builds and runs the plugin
Tests for the JavaScript (Node), the Swift (XCTest on a simulator, against cordova-ios and sentry-cocoa) and the Kotlin (Robolectric,
against cordova-android and sentry-android), cordova-paramedic tests, a demo app, coverage floors, and a CI that publishes only
when they pass, through npm trusted publishing (workflow ci.yaml)
